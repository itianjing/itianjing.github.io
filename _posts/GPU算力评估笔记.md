# GPU 算力评估笔记

> 本文面向零基础读者，从头建立 GPU 算力的完整认知框架。

---

## 引言：为什么要学 GPU 算力评估？

当你面对一张 GPU 的规格表，上面写着"FP32 82.6 TFLOPS""INT8 660 TOPS""AI 算力 1321 TOPS"——这些数字到底哪个代表真实性能？为什么同一张卡能同时标出好几个相差 10 倍的算力数字？买卡做 AI 训练、做大模型推理、做 3D 渲染，分别该看哪个指标？

本文的目标就是帮你建立一套完整的认知框架，让你读完以后能够：看懂 GPU 规格表上的每个数字、判断哪个数字对你的场景最重要、在不同 GPU 之间做公平的对比。

---

## 一、背景知识：先搞懂这些概念

### 1.1 GPU 是什么，为什么不用 CPU？

**CPU（中央处理器）** 和 **GPU（图形处理器）** 的最大区别是设计哲学不同：

| 特性 | CPU | GPU |
|------|-----|-----|
| 核心数量 | 少（8~128 核） | 多（数千~数万核） |
| 单核能力 | **强**（复杂逻辑、分支判断） | 弱（简单运算） |
| 擅长任务 | 串行复杂任务 | 大量简单任务**同时**并行 |
| 典型比喻 | 一个天才教授 | 一万个小学生同时算加法 |

**为什么 AI 要用 GPU**：训练神经网络的核心操作是对数百万个数字同时做相同的乘加运算（矩阵乘法）。这种"同一操作重复百万次"的模式完美匹配 GPU 的并行架构，而 CPU 只能一个一个算，慢几十倍到几百倍。

---

### 1.2 浮点数精度是什么意思（FP32、FP16、INT8...）

计算机存储数字需要占用内存，用的位数越多，精度越高，但计算也越慢、越费存储。

| 格式 | 全称 | 位数 | 能表示的范围 | 精度 | 典型用途 |
|------|------|------|------------|------|---------|
| **FP64** | 64 位双精度浮点 | 64 bit | 极大 | 极高（15 位有效数字） | 科学计算、金融 |
| **FP32** | 32 位单精度浮点 | 32 bit | 大 | 高（7 位有效数字） | 传统 GPU 计算、渲染 |
| **TF32** | 张量浮点（NVIDIA 专有） | 19 bit 有效精度 | 同 FP32 | 介于 FP16 和 FP32 之间 | AI 训练（A100+ 独有） |
| **BF16** | 脑浮点 16 | 16 bit | 同 FP32（指数位多） | 低 | AI 训练（谷歌发明，主流训练精度） |
| **FP16** | 16 位半精度浮点 | 16 bit | 小 | 低（3 位有效数字） | AI 训练/推理 |
| **INT8** | 8 位整数 | 8 bit | -128 ~ 127 | 极低（整数） | AI 推理（量化模型） |
| **FP8** | 8 位浮点 | 8 bit | 小 | 极低 | AI 推理（H100/L40S 起支持；消费级从 RTX 5090D 起支持） |
| **FP4** | 4 位浮点 | 4 bit | 很小 | 极低 | AI 推理（Blackwell 架构独有，最新量化精度） |

> **TF32 为什么存在**：FP32 精度高但计算慢，FP16 计算快但数字范围小（容易溢出）。TF32 是 NVIDIA 的折中方案：用 FP16 的位宽（10 位尾数）做矩阵乘计算（提高速度），累加时用 FP32 精度保留数字范围（保证不溢出）——在几乎不损失训练精度的前提下，算力提升约 7 倍。

> **为什么 AI 模型能容忍低精度？** 神经网络天然具有噪声鲁棒性——训练过程中梯度下降本身就带有随机性（如 dropout、数据增强），模型学到的不是精确的数值而是统计规律。因此把 FP32 换成 FP16 带来的微小舍入误差，对最终结果的影响通常可以忽略不计。这也是为什么 AI 领域能率先大规模使用低精度计算，而科学计算（如流体力学模拟）则必须坚守 FP64。

**直觉理解**：
- 用 FP32 存一个数字像用"1.2345678"，用 FP16 像用"1.23"，用 INT8 像用"1"
- 位数越少 → 每个数字占用存储越少 → 同样的显存能放更多数据 → GPU 处理更快
- AI 模型训练通常用 BF16/FP16，推理时可以进一步量化到 INT8/FP8，以换取更高的吞吐量

---

### 1.3 算力单位：TFLOPS 和 TOPS 是什么意思

**FLOPS = Floating Point Operations Per Second（每秒浮点运算次数）**

| 单位 | 含义 | 换算 |
|------|------|------|
| FLOPS | 每秒 1 次浮点运算 | 基准 |
| GFLOPS | 每秒 10 亿次 | 10⁹ FLOPS |
| **TFLOPS** | 每秒 1 万亿次 | 10¹² FLOPS |
| PFLOPS | 每秒 1000 万亿次 | 10¹⁵ FLOPS |

**TOPS = Tera Operations Per Second（每秒万亿次运算）**，和 TFLOPS 类似，但"Operations"包含整数运算（如 INT8），用于 AI 推理场景更多。

**直觉理解**：RTX 4090 的 FP32 算力是 82.6 TFLOPS，意味着它每秒能做 82.6 万亿次单精度浮点运算。一个人一秒能做 1~2 次运算，所以这相当于几十万亿人同时工作。

> **注意**：算力数字必须配合精度才有意义。同一张卡的 INT8 算力可能是 FP32 算力的 **8~16 倍**，因为 INT8 计算更简单、位宽更窄。

---

### 1.4 显存是什么（容量 vs 带宽，是两件事）

**显存（VRAM）** 是 GPU 自带的内存，专门存放 GPU 需要计算的数据（模型权重、中间结果等）。

显存有两个完全不同的重要指标：

| 指标 | 含义 | 类比 | 典型数值 |
|------|------|------|---------|
| **显存容量** | 能存多少数据 | 仓库的大小 | 24GB（RTX 4090）、80GB（H100） |
| **显存带宽** | 每秒能搬运多少数据 | 仓库到工厂的运输速度 | 1008 GB/s（RTX 4090）、3350 GB/s（H100） |

**两者缺一不可**：
- 容量不够 → 模型根本放不进去，卡直接报 OOM（Out of Memory）错误
- 带宽不够 → 模型能放进去，但 GPU 大量时间在等数据，算力白白浪费

**实际例子**：大模型（如 LLaMA-70B）的权重约 140GB（FP16），单张 H100（80GB）放不下，需要至少 2 张卡。放进去之后，每生成一个 token 都要把 140GB 权重从显存搬到计算单元，这时候带宽（3350 GB/s）决定了生成速度。

---

### 1.5 矩阵乘法为什么是 AI 的核心操作

神经网络的每一层，本质上都是在做"输入向量 × 权重矩阵 = 输出向量"。

用一个最简单的例子说明：

```
输入：[1, 2, 3]  （一句话里 3 个词的特征）

权重矩阵：
  [0.1, 0.4]
  [0.2, 0.5]
  [0.3, 0.6]

输出：[1×0.1 + 2×0.2 + 3×0.3,  1×0.4 + 2×0.5 + 3×0.6]
    = [1.4,  3.2]
```

这就是一次矩阵乘法。真实模型中：
- 输入向量可能有 **4096 维**（词的特征维度）
- 权重矩阵可能是 **4096×16384** 的规模
- 一次前向传播要做 **数百次**这样的矩阵乘法
- 同时处理 **一批（batch）** 输入，比如 512 条文本

这就是为什么需要专门的硬件（Tensor Core / Matrix Core / Cube Unit）来加速矩阵运算。

> **什么是 batch（批次）**：在深度学习中，batch 指一次同时送入模型处理的样本数量。比如 batch=512 意味着 GPU 同时计算 512 条文本，而不是一条一条算。更大的 batch 能更充分地利用 GPU 的并行能力，但也会消耗更多显存。

---

### 1.6 量化是什么（为什么推理可以用 INT8/FP8）

训练完的模型权重默认是高精度（FP32 或 FP16），**量化**是指在推理时把这些权重压缩成更低精度（INT8 或 FP8）的过程。

**为什么可以量化**：模型训练时需要高精度来保证梯度计算稳定，但训练好的模型在推理时，权重数值分布通常比较集中——大量权重值很小，用低精度表示的误差在可接受范围内。

**量化的收益**：
- 每个权重占用存储减半（FP16→INT8：16bit→8bit）
- 显存占用降低 → 可以跑更大的模型
- 数据搬运量减半 → 访存密集的 Decode 阶段直接提速
- INT8 Tensor Core 算力是 FP16 的 2 倍 → 计算更快

**量化的代价**：精度有轻微损失（通常 1%~3%），极端量化（FP4）损失更大，需要专门的校准和适配。

## 二、GPU 内部的核心计算单元

> **前置概念：SM（Streaming Multiprocessor，流式多处理器）**——NVIDIA GPU 的基本组织单元。一个 GPU 芯片由数十到上百个 SM 组成，每个 SM 内部包含若干 CUDA Core、Tensor Core、寄存器、共享内存等。比如 RTX 4090 有 128 个 SM，每个 SM 含 128 个 CUDA Core 和 4 个 Tensor Core。理解 SM 是理解 GPU 架构的起点——你看到的"CUDA Core 数量"和"Tensor Core 数量"本质上就是 SM 数量 × 每 SM 所含数量。

### 2.1 NVIDIA 的两类核心单元

NVIDIA GPU 内部有两种最重要的计算单元，功能完全不同：

#### CUDA Core（通用计算单元）

- **做什么**：处理**标量**运算，即一次处理一个数字
- **每时钟周期**：完成一次浮点乘加（a × b + c，即一次 FMA 操作）
- **主要精度**：FP32（单精度）、FP64（双精度）
- **适合**：渲染着色器、通用并行计算、逐元素操作（激活函数等）

#### Tensor Core（矩阵运算专用加速单元）

- **做什么**：专门加速**矩阵乘累加**运算，一次处理一整个小矩阵
- **每时钟周期**：完成一个 4×4 矩阵乘累加（相当于 64 次乘加，是 CUDA Core 的 64 倍）
- **支持精度**：FP16、BF16、TF32、INT8、FP8（混合精度：输入低精度，累加用 FP32 保证精度）
- **适合**：深度学习训练、推理（核心计算）

**关键数字对比（以 RTX 4090 为例）**：

```
CUDA Core FP32 算力:   82.6 TFLOPS   ← 通用计算
Tensor Core FP16 算力: ~330 TFLOPS   ← AI 矩阵计算，是前者的 4 倍
Tensor Core INT8 算力: ~660 TOPS     ← AI 推理量化，是 FP32 的 8 倍
```

同一张卡，不同单元、不同精度下的算力数字可以差 **8 倍以上**，这就是为什么看 GPU 规格时必须搞清楚"这个数字是哪种单元、哪种精度"。

---

### 2.2 读懂厂商规格表

NVIDIA 官方规格表（以 H100 为例，因为 H100 覆盖的精度最全）的典型标注方式：

```
FP64:        34 TFLOPS         ← CUDA Core（双精度，科学计算）
FP32:        67 TFLOPS         ← CUDA Core（单精度，通用/渲染）
TF32:        494 TFLOPS        ← Tensor Core（AI 训练，NVIDIA 专有格式）
BF16/FP16:   989 TFLOPS        ← Tensor Core（AI 训练主流精度）
INT8:        1979 TOPS         ← Tensor Core（AI 推理量化）
FP8:         1979 TOPS         ← Tensor Core（Hopper 架构新增，超高速推理）
```

> **注意**：以上均为 Dense（稠密）模式下的理论峰值算力。厂商标注的是理论最大值，实际持续性能会受功耗墙和散热限制，长时间满载运行时可能低于标称值。

**识别规律**：
- 看到 **FP32 / FP64** → 基本是 CUDA Core 的数字
- 看到 **TF32 / BF16 / FP16 / INT8 / FP8** → 基本是 Tensor Core 的数字
- 数值**越来越大**：每降一级精度，算力翻约 1~2 倍

---

### 2.3 两个容易踩的坑

**坑 1：FP16 有两种算力，差 4 倍**

同一张卡的 FP16 算力根据核心类型不同，差距很大：
- **CUDA Core 的 FP16**：与 FP32 相当，**没有额外加速**（即算精度减半，速度不变）
- **Tensor Core 的 FP16**：是 FP32 的 **4 倍**（专用矩阵加速器，每时钟处理更多数据）

厂商宣传时只写 "FP16: 330 TFLOPS" 但不说明是哪种核心时，**大概率是 Tensor Core 的数字**（因为更大更好看）。

**坑 2：Dense vs Sparse（稠密 vs 稀疏）**

NVIDIA Ampere 架构（A100）之后，Tensor Core 支持"2:4 结构化稀疏"加速：
- 将模型权重中 50% 的不重要参数设为 0
- Tensor Core 跳过这些 0 值，**吞吐量翻倍**
- 同一指标有两个数字：**Dense（实际算力）** 和 **Sparse（开启稀疏后翻倍）**

很多宣传材料**只写 Sparse 的大数字**，不标注是稀疏模式，让卡看起来比实际强一倍。

> **建议**：对比时统一看 **Dense 数字**，更真实可靠。

## 三、GPU 使用场景与核心需求

不同场景对 GPU 的诉求完全不同，理解这一点才能正确选型。

### 场景总览

| 场景 | 主要计算单元 | 精度要求 | 主要瓶颈 | 特殊需求 |
|------|------------|---------|---------|---------|
| DL 训练 | Tensor Core | BF16/FP16 | 显存**容量** | NVLink 多卡互联 |
| DL 推理 | Tensor Core | INT8/FP8 | 显存**带宽** | 功耗效率 |
| 图形渲染 | CUDA Core | FP32 | 显存带宽 | RT Core（光追） |
| 科学计算 | CUDA Core | **FP64** | 显存带宽+容量 | ECC 纠错显存 |
| 视频处理 | NVENC/NVDEC | — | 显存带宽 | 编解码路数 |

---

### 3.1 深度学习训练

**核心诉求：Tensor Core FP16/BF16 算力 + 显存容量 + 多卡互联带宽**

| 关键指标 | 重要程度 | 原因 |
|----------|:--------:|------|
| Tensor Core BF16/FP16 算力 | **最高** | 前向/反向传播的核心计算全靠矩阵乘 |
| 显存容量 | **极高** | 模型参数 + 优化器状态 + 梯度，大模型动辄需要几十到上百 GB |
| 显存带宽 | 高 | 大 batch 下权重搬运频繁 |
| 多卡互联 (NVLink/PCIe) | **极高** | 分布式训练的通信开销直接决定扩展效率 |
| FP32 CUDA 算力 | 低 | 训练几乎不走 CUDA Core |

**典型场景**：大语言模型预训练、图像/视频模型训练、推荐系统

**适配卡型**：H100/H200、A100、L40S

#### GPU 在训练时具体做什么

**① 前向传播（Forward Pass）**

把原始数据"喂"过整个神经网络，得到一个预测结果。

- 以 LLM 为例：输入一批 token → Embedding 查表变成向量 → 每个 Transformer 层做：
  - **自注意力（Self-Attention）**：`Q × K^T` 矩阵乘法 → 注意力分数 → 加权求和
  - **前馈网络（FFN）**：两层全连接变换（又是矩阵乘法）
- 最终输出每个位置的下一个 token 概率分布
- **为什么吃 Tensor Core**：这些操作全是大规模并行的矩阵乘法，占训练 90%+ 的计算时间

**② 反向传播（Backward Pass）**

从预测结果倒推，算出每个权重"应该往哪个方向调、调多少"（即梯度）。

- 用 Loss 函数算出预测与正确答案的差距
- 用**链式法则**从 loss 逐层往回算梯度
- 每一层的梯度计算 = **上层梯度 × 本层权重的转置** → 又是矩阵乘法
- **每一层反向传播需要做 2 次矩阵乘法**，计算量和前向传播差不多

**③ 参数更新（Optimizer Step）**

用算出来的梯度，实际修改模型权重。

- 实际中几乎都用 **Adam 优化器**：额外维护一阶动量 m 和二阶动量 v
- 对大模型而言，优化器状态 (m, v) 大小是模型参数的 **2 倍**
- 例：70B 参数模型（FP16 约 140GB），优化器状态额外需 **280GB FP32 显存**
- 这就是为什么训练大模型对**显存容量**要求极高的核心原因

---

### 3.2 深度学习推理

**核心诉求：低精度算力 (INT8/FP8) + 显存带宽 + 低延迟**

| 关键指标 | 重要程度 | 原因 |
|----------|:--------:|------|
| INT8/FP8 Tensor 算力 | **最高** | 量化推理追求极致吞吐 |
| 显存带宽 | **极高** | Decode 阶段是 memory-bound，带宽决定 token/s |
| 显存容量 | 高 | 需要装下完整模型权重 |
| CUDA Core 算力 | 低 | 推理基本不走 FP32 |
| 功耗效率 (TOPS/W) | 高 | 推理服务 7×24 小时不间断运行，1 张 H100（700W）一年电费约 3~5 万元；算力/功耗比直接影响长期运营成本 |

**典型场景**：LLM 在线服务、图像生成推理、自动驾驶实时推理

**适配卡型**：H100/H200、L40S、RTX 4090/4090D（小模型本地推理，仅支持 INT8 量化，不支持 FP8）

#### GPU 在推理时具体做什么（以 LLM 为例）

推理分为截然不同的两个阶段：

**① Prefill 阶段（处理 Prompt）**

用户输入一整段 prompt，GPU 并行处理所有 token，一次性"理解"整段话。

- 用户输入 15 个 token → GPU 同时送进模型做前向传播
- 自注意力中：15 个 token 互相计算注意力分数 → `15×15` 矩阵 → 加权求和
- 每层结束后保存中间结果到 **KV Cache**（Key-Value 缓存：存储每层 Attention 计算中间结果，供 Decode 阶段复用，避免重复处理整段 Prompt；显存占用随 token 数线性增长）
- **计算密集**：token 越多，矩阵越大，计算量按 token 数的**平方**增长，GPU 利用率 70%~90%

**② Decode 阶段（逐 Token 生成）**

一个 token 一个 token 地"写"回答，每写一个都要把整个模型权重翻一遍。

- 将单个 token 送入模型做前向传播
- 每层权重（可能几十 GB）从显存搬到计算单元，但实际只做很小的矩阵乘
- **访存密集**（用具体数字说明）：
  - LLaMA-70B，FP16 权重约 **140GB**
  - 每生成一个 token，要把 140GB 权重全部读一遍
  - H100 显存带宽 3350 GB/s → 读一遍需 ≈ 42ms → 理论最快 ~24 token/s
  - 而算力只需 0.14ms → **GPU 99.7% 的时间在等数据搬运，算力几乎全部浪费**

> **关键结论**：大模型推理（Decode 阶段）的瓶颈不是算力，而是**显存带宽**。选卡时带宽比算力更重要。

---

### 3.3 图形渲染 / 游戏 / 可视化

**核心诉求：CUDA Core FP32 算力 + 光追核心 (RT Core) + 显存带宽**

| 关键指标 | 重要程度 | 原因 |
|----------|:--------:|------|
| FP32 CUDA Core 算力 | **最高** | 着色器计算、几何处理的主战场 |
| RT Core 性能 | 高 | 光线追踪加速（如果开启） |
| 显存带宽 | 高 | 高分辨率纹理搬运 |
| 显存容量 | 中 | 4K 渲染约需 8-16GB |
| Tensor Core | 低（除 DLSS） | 仅 DLSS/帧生成等 AI 功能用到 |

**典型场景**：3D 游戏、影视特效渲染、建筑可视化、CAD

**适配卡型**：RTX 4090/4080（消费级）、RTX 6000 Ada（专业级）

#### GPU 渲染一帧画面的流水线

**① 顶点处理（Vertex Shader）**

把 3D 模型的"骨架"从模型坐标系变换到屏幕 2D 位置。

- 经过 3 个矩阵乘法：模型矩阵（放到世界中）→ 视图矩阵（从摄像机角度看）→ 投影矩阵（3D 投影到 2D，产生近大远小效果）
- 数百万顶点独立执行相同变换 → 完美适合 GPU 并行

**② 光栅化（Rasterization）**

把三角形"涂色"成像素。

- 遍历每个三角形覆盖的屏幕像素，对 3 个顶点属性做插值（颜色、法线、深度等）
- 深度测试：被更近三角形覆盖的像素丢弃
- 现代游戏场景可能有**数百万三角形**，产生**数十亿像素片段**

**③ 片段着色（Fragment/Pixel Shader）—— 最吃算力的环节**

计算每个像素最终显示什么颜色。

- **纹理采样**：从 2K~8K 纹理贴图中查出颜色
- **光照计算（PBR）**：漫反射 + 镜面反射 + 环境光遮蔽 + 金属度/粗糙度，可能受十几个光源影响
- **阴影判断**：Shadow Map 采样判断是否在阴影中
- 算力需求：4K = 830 万像素 × 60fps = 每秒 **5 亿次着色器调用**，全靠 CUDA Core FP32

**④ 光线追踪（Ray Tracing）**

模拟真实光线的物理行为，从相机发射光线追踪弹射路径。

- 每个像素从相机发射一条光线 → 击中三角形 → 按材质弹射次级光线（3~8 次）
- 4K 分辨率可能需要处理**数亿条光线**，每条要和场景数百万三角形做求交测试
- **RT Core 加速 BVH 遍历**：把场景组织成包围盒树，快速排除不相交三角形，速度提升数十倍

---

### 3.4 科学计算 / HPC

**核心诉求：CUDA Core FP64 算力 + 显存带宽 + ECC 显存**

| 关键指标 | 重要程度 | 原因 |
|----------|:--------:|------|
| FP64 CUDA Core 算力 | **最高** | 科学模拟对双精度有硬性要求 |
| 显存带宽 | **极高** | CFD、分子动力学等是典型访存密集 |
| 显存容量 | 高 | 大规模网格/粒子模拟数据量大 |
| ECC 纠错 | **必须** | 长时间计算不容许比特翻转错误 |
| Tensor Core | 不用 | HPC 基本不用混合精度 |

> **ECC（纠错码）**：一种特殊的显存技术，能检测并纠正随机的比特翻转错误（宇宙射线或硬件噪声导致）。科学计算需要长时间运行，一个比特错误可能让几天的计算结果全部作废，所以必须要 ECC。消费级 GPU（如 RTX 4090）通常不支持 ECC。

**典型场景**：流体力学 (CFD)、分子动力学、气象模拟、量子化学

**适配卡型**：H100、A100、H200（消费级卡 FP64 被大幅阉割，不适合）

**为什么必须 FP64**：科学模拟涉及迭代求解，微小的浮点误差会在数百万次迭代后累积放大，导致结果完全不可用。FP32 约 7 位有效数字，FP64 约 15 位，差了一亿倍。

#### GPU 在科学计算中做什么

**计算流体力学（CFD）**：把流体空间切成数百万~数亿个小格子，用 Navier-Stokes 方程每个时间步更新每个格子的速度、压力、温度，模拟 1 秒可能需要数万个时间步。

**分子动力学（MD）**：模拟数百万个原子之间的相互作用力，用牛顿第二定律 F=ma 更新每个原子的速度和位置，模拟 1 微秒生物过程需要 50 万~100 万个时间步。

**有限元分析（FEA）**：把复杂形状（飞机机翼、桥梁）离散为有限个网格，组装成大型稀疏线性方程组 Ku = F，求解每个节点的位移和应力。

---

### 3.5 视频编解码 / 多媒体处理

**核心诉求：专用编解码单元 (NVENC/NVDEC) + 显存带宽**

| 关键指标 | 重要程度 | 原因 |
|----------|:--------:|------|
| NVENC/NVDEC 数量与版本 | **最高** | 硬件编解码，与 CUDA/Tensor Core 完全无关 |
| 显存带宽 | 高 | 多路高分辨率视频流吞吐 |
| CUDA Core 算力 | 中 | 后处理（缩放、滤镜）会用到 |
| Tensor Core | 中 | AI 超分辨率等增强功能 |

**典型场景**：直播推流、视频转码、云游戏、视频 AI 分析

**适配卡型**：L40S、T4、RTX 40 系列（NVENC 支持 AV1）

#### GPU 在视频处理中做什么

- **NVDEC（解码）**：将 H.264/H.265/AV1 压缩流解码为原始帧。**不走 CUDA/Tensor Core**，由专用硬件单元独立完成。
- **NVENC（编码）**：将原始帧压缩为 H.264/H.265/AV1，同样是专用硬件。
- **视频后处理（CUDA Core）**：缩放、色彩空间转换（YUV→RGB）、叠加水印。
- **视频 AI 分析（Tensor Core）**：目标检测、人脸识别——解码后的帧送入推理模型。

**为什么主要看 NVENC/NVDEC**：编解码是固定功能硬件加速，一张卡能同时处理多少路视频取决于编解码器单元数量，而非 CUDA Core 数量。

---


### 3.6 场景小结：为什么"算力大就是好"是个陷阱

读完前五个场景，可以归纳出一个关键规律：**每个场景真正在乎的指标都不一样**。

| 场景 | 真正的瓶颈 | 对应指标 |
|------|----------|---------|
| DL 训练 | 矩阵乘法吞吐 | Tensor Core BF16 算力 |
| 大模型推理 Decode | 显存搬运速度 | 显存带宽 |
| 图形渲染 | 逐像素着色计算 | CUDA Core FP32 算力 |
| 科学计算 | 双精度迭代精度 | CUDA Core FP64 算力 |
| 视频处理 | 编解码路数 | NVENC/NVDEC 数量 |

这就产生了一个问题：**GPU 厂商的宣传材料里，同一张卡可以同时标注出 5~6 个差异悬殊的算力数字**（从几十 TFLOPS 到近 2000 TOPS）。如果不知道自己的场景该看哪个数字，就很容易被"最大的那个数字"迷惑——而厂商往往故意把最大的数字放在最显眼的位置。

**一个典型的误导案例**：

> 某厂商宣传"AI 算力高达 **2000 TOPS**"——这是 INT8 Tensor Core Sparse 模式的峰值数字。
>
> 但如果你的任务是 **FP64 科学计算**，这张卡实际可用算力可能只有 **20 TFLOPS**，差了 **100 倍**。
>
> 如果你的任务是 **大模型 Decode 推理**，真正的瓶颈是显存带宽，2000 TOPS 的算力对实际速度几乎没有帮助。

**如何拆解厂商的"AI TOPS"营销数字**：

近年来 NVIDIA 等厂商在消费级显卡上主推一个叫"**AI TOPS**"的宣传指标（如 RTX 5090D 标称 3352 AI TOPS）。这个数字的构成是：

```
AI TOPS = 最高支持精度 × Sparse（稀疏）模式 × 理论峰值
```

以 5090D 为例：3352 AI TOPS = FP4 精度 × 2:4 稀疏翻倍 × 理论峰值。它同时叠加了"最低精度"和"稀疏加速"两个放大系数，因此是所有算力数字中最大的那个。厂商把它放在规格页最显眼的位置，但实际能否用上取决于：① 你的模型是否支持 FP4 量化；② 模型权重是否满足 2:4 结构化稀疏的格式要求。两项条件同时满足才能接近这个数字，否则实际可用算力可能只有宣传值的 1/4 甚至更低。

**这就是为什么需要一套严格的对比方法论**——在看任何 GPU 的算力数字之前，必须先做"四个对齐"，否则数字没有任何意义。

---

## 四、跨卡对比的正确方法

### 核心原则：四个对齐

**对齐精度、对齐核心类型、对齐稠密/稀疏、对齐瓶颈，否则数字毫无意义。**

---

### 4.1 对齐精度

**不同精度之间的算力数字不能直接比较。** 同一个 GPU 在不同精度下算力可以差 10 倍以上：

```
H100 SXM 算力全景（Dense）：
FP64:     34 TFLOPS      ← 基准线
FP32:     67 TFLOPS      ← FP64 的 2 倍
TF32:     494 TFLOPS     ← FP32 的 7.4 倍
BF16:     989 TFLOPS     ← TF32 的 2 倍
INT8:     1979 TOPS      ← BF16 的 2 倍
FP8:      1979 TOPS      ← 同 INT8
```

**常见错误**：拿 A 卡的 "INT8 1000 TOPS" 对比 B 卡的 "FP32 50 TFLOPS"，得出 "A 卡快 20 倍" → 完全错误，这两个数字根本不在同一维度。

**正确做法**：先确定你的场景需要什么精度，再只比较该精度下的算力。

---

### 4.2 对齐核心类型

**CUDA Core 算力和 Tensor Core 算力不能混着比。**

以 RTX 4090 为例，同样是"FP16 算力"，差 4 倍：

```
FP32 CUDA Core 算力:   82.6 TFLOPS
FP16 CUDA Core 算力:   ~82.6 TFLOPS（Ada 架构）
FP16 Tensor Core 算力: ~330 TFLOPS（不带 Sparsity）
```

**怎么识别**：FP16 算力远大于 FP32 算力（4 倍以上）→ 一定是 Tensor Core 的数字

---

### 4.3 对齐稠密/稀疏（Dense vs Sparse）

```
H100 SXM BF16:
Dense:   989 TFLOPS    ← 实打实的算力
Sparse:  1979 TFLOPS   ← 开启 2:4 稀疏后翻倍（需模型支持）
```

**建议**：对比时默认使用 **Dense 数字**，Sparse 需要模型专门优化才能用上。

---

### 4.4 对齐瓶颈（算力 vs 带宽）

**光比算力不够，还要判断你的任务是"算力密集型"还是"访存密集型"。**

| 指标 | 含义 | 影响场景 |
|------|------|---------|
| 算力（TFLOPS/TOPS） | 每秒计算次数上限 | 计算密集型任务 |
| 显存带宽（GB/s） | 每秒数据搬运上限 | 访存密集型任务 |
| 算术强度（FLOP/Byte） | 每搬 1 字节能做几次计算（越高越适合 GPU，越低则越受带宽限制） | 判断任务属于哪种类型 |

**实际案例 —— H100 vs A100 跑 LLM 推理**：

| 指标 | A100 | H100 | 比值 |
|------|------|------|------|
| BF16 Tensor 算力 (Dense) | 312 TFLOPS | 989 TFLOPS | 3.2x |
| 显存带宽 | 2039 GB/s | 3350 GB/s | 1.6x |

只看算力，H100 应快 3.2 倍。但 LLM Decode 阶段是**访存密集型**，实际加速比更接近带宽比 **1.6x**。

> 这就是为什么只看 TFLOPS 会严重高估实际性能差距。

---

### 4.5 估算实际加速比

- **计算密集任务**（大 batch 矩阵乘、训练）：实际加速比 ≈ 算力比值 × 0.7~0.9
- **访存密集任务**（大模型推理 Decode）：实际加速比 ≈ 带宽比值 × 0.8~0.95
- **多卡训练**：还要考虑互联带宽（NVLink 远优于 PCIe）

> **PCIe 带宽为何重要**：当没有 NVLink 时（如消费级显卡之间），多卡通信只能走 PCIe。PCIe 各代带宽差异显著：PCIe 3.0 x16 单向约 16 GB/s，PCIe 4.0 x16 约 32 GB/s，PCIe 5.0 x16 约 64 GB/s。相比之下，H100 的 NVLink 4.0 单向带宽可达 450 GB/s，是 PCIe 5.0 的 7 倍。因此分布式训练中，消费级多卡方案（如多张 RTX 4090）的通信效率远低于数据中心卡（如 H100），这是选型时容易忽略的隐藏瓶颈。

> **为什么不是 1.0？** 理论峰值算力是 GPU 在理想条件下能达到的最大值，但实际运行中存在多种损耗：软件栈（驱动、CUDA 运行时）的调度开销、算子实现并非 100% 最优、内存访问延迟、以及多卡通信的同步等待等。综合这些因素，实际能达到的性能通常只有理论峰值的 70%~90%。访存密集任务的折扣系数略高（0.8~0.95），因为带宽利用率通常比算力利用率更容易接近理论值。

---

### 4.6 实战对比模板

```
=== GPU 对比清单 ===

Step 1. 基础规格对齐
   架构、CUDA Cores、Tensor Cores、显存容量、
   显存类型(HBM/GDDR)、显存带宽、TDP、多卡互联方式

Step 2. 算力对齐（同精度、同核心、Dense 口径）
   FP64 (CUDA Core) | FP32 (CUDA Core) | TF32 (Tensor, Dense)
   BF16 (Tensor, Dense) | INT8 (Tensor, Dense) | FP8 (Tensor, Dense)

Step 3. 根据目标场景选指标
   - DL 训练         → BF16 Dense 算力比值
   - DL 推理         → INT8/FP8 Dense 算力 + 显存带宽
   - 大模型推理 Decode → 主要看显存带宽比值
   - 科学计算         → FP64 算力
   - 渲染            → FP32 算力

Step 4. 估算实际加速比（乘以 0.7~0.9 折扣）
```

---

### 4.7 常见对比误区

| 误区 | 为什么错 | 正确做法 |
|------|---------|---------|
| 直接比 TFLOPS 大小 | 没对齐精度和核心类型 | 先锁定精度+核心类型再比 |
| 用 Sparse 数字对比 Dense 数字 | 口径不一致 | 统一用 Dense |
| 只看算力不看带宽 | 访存密集场景会严重误判 | 按场景取主要瓶颈指标 |
| 用理论算力推算实际性能 | 忽略软件优化、算子效率 | 按 0.7~0.9 的折扣系数估算 |
| 忽略多卡互联差异 | NVLink 和 PCIe 差距巨大 | 多卡场景必须看互联带宽 |
| 忽略显存容量 | 模型放不下卡就用不了 | 先确认容量够，再比算力 |

---

> 掌握了四个对齐方法论之后，本章用两个真实案例来实战演练，看看同样的方法论如何应用在具体的选卡决策中。

## 五、具体卡型对比

### 5.1 RTX 4090D vs 5090D

两张卡均为 NVIDIA 针对中国市场的合规版本（D 代表专为中国市场设计的合规版），跨越 Ada Lovelace（4090D）到 Blackwell（5090D）两代架构。

> **什么是"D 版"**：由于出口管制要求，NVIDIA 专门为中国市场设计了性能受限的版本。4090D 削减了约 11% 的 CUDA Core；而 5090D 核心规格与国际版 5090 **完全相同**，限制体现在其他层面。

| 指标 | RTX 4090D | RTX 5090D | 倍率 |
|------|-----------|-----------|------|
| 架构 | Ada Lovelace | Blackwell | — |
| CUDA Cores | 14592 | 21760 | **+49%** |
| Tensor Cores | 456 (4th Gen) | 680 (5th Gen) | +49%（数量） |
| **FP32 (CUDA)** | ~74 TFLOPS | ~104.9 TFLOPS | **+42%** |
| **FP16 Tensor (Dense)** | ~294 TFLOPS | ~660 TFLOPS | **~2.2x** |
| **FP8 Tensor (Dense)** | 不支持 | ~1321 TOPS | **独有（消费级首次支持）** |
| **FP4 Tensor (Dense)** | 不支持 | ~1678 TFLOPS | **独有** |
| AI TOPS（宣传峰值） | 1321 TOPS (FP8 Sparse) | 3352 TOPS (FP4 Sparse) | **~2.5x** |
| 显存 | 24GB GDDR6X | 32GB GDDR7 | +33% 容量 |
| 显存带宽 | 1008 GB/s | 1792 GB/s | **+78%** |
| TDP | 425W | 575W | +35% |
| 总线接口 | PCIe Gen4 x16 | PCIe Gen5 x16 | — |

**关键判断**：

1. **深度学习训练/推理**：5090D 的 FP16 Dense 算力比 4090D 提升约 **2.2 倍**（660 vs ~294 TFLOPS），且 5090D 独有 FP4/FP8 支持带来额外量化推理优势
2. **大模型推理 Decode（访存密集）**：显存带宽提升 **78%**，实际速度提升接近 1.8 倍
3. **图形渲染**：FP32 算力提升 42%，帧率提升约 **30~40%**（还受驱动、游戏优化影响）
4. **"3352 AI TOPS"的水分**：这是 FP4 + Sparse 模式的峰值，5090D 独有 FP4 支持确实是代际优势，但要用上需要模型专门适配 FP4 量化；同口径（FP16 Dense）对比提升约 2.2 倍
5. **显存容量升级明显**：从 24GB 到 32GB，能跑更大的模型（FP16 下约可装下 16B 参数模型）

> **注意**：5090D 核心规格与国际版 5090 基本相同（部分来源显示 5090D 总线接口可能为 PCIe 4.0，5090 国际版为 PCIe 5.0，选型时建议核实最新官方信息）；4090D 相较 4090 国际版 CUDA Core 少约 11%（14592 vs 16384），Tensor Core 同比削减（456 vs 512），AI 算力也相应降低约 10%，渲染场景弱约 10%。

---

### 5.2 A100 vs H100

两代数据中心 GPU，架构代际差异巨大。

| 指标 | A100 (80GB SXM) | H100 (80GB SXM) | 倍率 |
|------|-----------------|-----------------|------|
| 架构 | Ampere | Hopper | — |
| CUDA Cores | 6912 | 16896 | 2.4x |
| Tensor Cores | 432 (3rd Gen) | 528 (4th Gen) | 1.2x（数量） |
| FP64 (CUDA) | 9.7 TFLOPS | 34 TFLOPS | **3.5x** |
| FP32 (CUDA) | 19.5 TFLOPS | 67 TFLOPS | **3.4x** |
| TF32 Tensor (Dense) | 156 TFLOPS | 494 TFLOPS | **3.2x** |
| BF16/FP16 Tensor (Dense) | 312 TFLOPS | 989 TFLOPS | **3.2x** |
| INT8 Tensor (Dense) | 624 TOPS | 1979 TOPS | **3.2x** |
| FP8 Tensor (Dense) | 不支持 | 1979 TOPS | **独有** |
| 显存 | 80GB HBM2e | 80GB HBM3 | 同容量 |
| 显存带宽 | 2039 GB/s | 3350 GB/s | **1.6x** |
| TDP | 400W | 700W | +75% |

**关键判断**：

1. **AI 训练/推理算力**：H100 比 A100 快 **3.2 倍**（Tensor Core Dense）
2. **科学计算 (FP64)**：H100 比 A100 快 **3.5 倍**
3. **大模型推理实际速度**：H100 比 A100 快约 **1.6~2 倍**（带宽瓶颈，非算力瓶颈）
4. **FP8 是 H100 独有**：支持更激进的量化推理

> **功耗与散热提示**：H100 的 TDP 高达 700W，比 A100（400W）高出 75%。数据中心部署时，功耗直接决定电费成本和散热方案（风冷 vs 液冷）。单张 H100 一年 24/7 满载运行的电费可达数万元人民币（按工业电价约 0.6~1 元/度估算）。在选型时，TDP 和散热需求是不可忽视的实际因素。

---

> 前面的所有讨论都基于 NVIDIA 的术语体系（CUDA Core、Tensor Core 等）。但实际工作中你可能接触到 AMD 和华为昇腾的产品，它们有各自的命名体系。本章建立三者之间的对应关系，方便跨平台沟通和选型。

## 六、三大厂商核心单元命名对照

### 6.1 整体对照表

| 功能 | NVIDIA | AMD | 华为昇腾 |
|------|--------|-----|---------|
| **通用计算单元** | CUDA Core | Stream Processor (SP) | Scalar Unit（AICore 内部） |
| **矩阵/AI 加速单元** | Tensor Core | Matrix Core（CDNA）/ AI Accelerator（RDNA） | Cube Unit（达芬奇架构） |
| **光线追踪单元** | RT Core | Ray Accelerator | 不支持（非渲染卡） |
| **视频编码** | NVENC | VCE / VCN | DVPP（数字视觉预处理器） |
| **视频解码** | NVDEC | UVD / VCN | DVPP |
| **通用编程模型** | CUDA | ROCm / HIP | CANN |
| **显存类型（高端）** | HBM3 / GDDR6X | HBM3 / GDDR6 | HBM2e（910B） |
| **多卡互联** | NVLink / NVSwitch | Infinity Fabric | HCCS |

---

### 6.2 逐项详细说明

#### 通用计算单元

**NVIDIA：CUDA Core**
- 正式名称 CUDA Core，每个时钟做一次 FP32 FMA（乘加）
- 通用并行计算的基础单元

**AMD：Stream Processor（流处理器，SP）**
- AMD 从不用 "CUDA Core"（CUDA 是 NVIDIA 的品牌）
- AMD 官方叫 **Stream Processor** 或 **Shader Processor**
- 一个 Compute Unit（CU）包含 64 个 Stream Processor
- 功能上和 CUDA Core 基本对应，但架构实现不同

**华为昇腾：AICore 内的 Scalar Unit**
- 昇腾芯片的核心计算单元叫 **AICore**，内部包含多个子单元
- **Scalar Unit**：负责通用标量计算（对应 CUDA Core）
- **Vector Unit**：负责向量运算（逐元素操作）
- **Cube Unit**：负责矩阵乘法（对应 Tensor Core，见下）

---

#### 矩阵/AI 加速单元（最关键）

**NVIDIA：Tensor Core**
- 支持 FP16、BF16、TF32、INT8、FP8 等混合精度矩阵乘累加
- 深度学习的核心加速硬件

**AMD：Matrix Core / AI Accelerator**
- **数据中心卡（CDNA 架构，如 MI300X）**：叫 **Matrix Core**，支持 FP16、BF16、INT8
- **消费级卡（RDNA 3 架构，如 RX 7900）**：叫 **AI Accelerator**，支持 INT8/FP8
- 功能上对标 Tensor Core，但 AMD 从不用 Tensor 这个词

**华为昇腾：Cube Unit（达芬奇架构）**
- 昇腾芯片采用自研的**达芬奇架构（Da Vinci Architecture）**
- AICore 内部的矩阵计算硬件叫 **Cube Unit**
- 每个 Cube Unit 一个时钟周期可完成一个 **16×16×16** 的 FP16 矩阵乘累加（4096 次乘加）
- 比 NVIDIA Tensor Core 的 4×4 单元规模大得多（但实际吞吐还需看频率和数量）

---

#### 光线追踪单元

**NVIDIA：RT Core** — 专用硬件加速 BVH 遍历 + 光线-三角形求交

**AMD：Ray Accelerator** — RDNA 2 架构引入，每个 CU 内置一个，功能对标 RT Core

**华为昇腾：无** — 昇腾定位是 AI 计算卡，不做图形渲染

---

#### 编程模型（软件层）

这一层的差异对开发者影响最大：

| 特性 | NVIDIA CUDA | AMD ROCm/HIP | 华为 CANN |
|------|------------|--------------|---------|
| 生态成熟度 | **最强** | 中等，近年快速追赶 | 相对封闭，主要国内 |
| 与 PyTorch 集成 | 原生支持 | 支持（via ROCm） | 支持（需适配层） |
| 与主流框架集成 | 原生支持 | 支持 | 以 MindSpore 为主 |
| 从 CUDA 迁移难度 | — | 中（HIP 工具可辅助） | 较大 |
| 算子库 | cuBLAS、cuDNN | rocBLAS、MIOpen | AscendCL、CANN 算子库 |

---

#### 多卡互联

**NVIDIA：NVLink / NVSwitch**
- NVLink 是点对点高速互联，NVSwitch 是多卡交换芯片
- H100 SXM：NVLink 4.0，8 卡全互联总带宽 3.6 TB/s

**AMD：Infinity Fabric**
- AMD CPU 和 GPU 都用 Infinity Fabric 互联
- MI300X（纯 GPU 形态）：多个 GPU die 通过 Infinity Fabric 互联，共享 192GB HBM3（注意：APU 形态的是 MI300A，将 CPU 与 GPU 集成在同一封装，配备 128GB HBM3）

**华为昇腾：HCCS（高速缓存一致性互联）**
- 昇腾 910B 支持 HCCS 多卡互联
- 带宽和 NVLink 相比仍有差距，但在国产集群中作为替代方案使用

---

### 6.3 一句话对应关系总结

```
CUDA Core       ≈   Stream Processor (AMD)    ≈   Scalar Unit in AICore (昇腾)
Tensor Core     ≈   Matrix Core (AMD CDNA)    ≈   Cube Unit in AICore (昇腾)
RT Core         ≈   Ray Accelerator (AMD)     ≈   无 (昇腾)
NVENC/NVDEC     ≈   VCE/VCN (AMD)            ≈   DVPP (昇腾)
CUDA            ≈   ROCm/HIP (AMD)            ≈   CANN (昇腾)
NVLink          ≈   Infinity Fabric (AMD)     ≈   HCCS (昇腾)
```

**最大差异**：NVIDIA 的这些单元名称已成为行业事实标准，很多场景下大家直接用 NVIDIA 的名词讨论。AMD 和昇腾都有自己的体系，跨平台对比时需明确说明是哪家的架构和对应单元。

## 七、速查表

### 场景 → 看哪个指标

| 场景 | 主要指标 | 次要指标 |
|------|---------|---------|
| DL 训练 | Tensor Core BF16/FP16 Dense TFLOPS | 显存容量、NVLink 带宽 |
| DL 推理 | Tensor Core INT8/FP8 Dense TOPS | 显存带宽、功耗效率 |
| 大模型推理 (Decode) | **显存带宽** (GB/s) | 显存容量、Tensor Core 算力 |
| 3D 渲染 | CUDA Core FP32 TFLOPS | RT Core、显存带宽 |
| 科学计算 | CUDA Core FP64 TFLOPS | 显存带宽、ECC |
| 视频处理 | NVENC/NVDEC 路数 | 显存带宽 |

### 精度 → 计算单元归属

| 精度 | 归属核心 | 典型用途 |
|------|---------|---------|
| FP64 | CUDA Core | 科学计算 |
| FP32 | CUDA Core | 渲染、通用计算 |
| TF32 | Tensor Core | AI 训练（NVIDIA 专有） |
| BF16 / FP16 | Tensor Core | AI 训练主流 |
| INT8 / FP8 | Tensor Core | AI 推理量化 |

### 估算实际加速比

- **计算密集任务**（训练、Prefill）：实际加速比 ≈ 算力比值 × 0.7~0.9
- **访存密集任务**（大模型推理 Decode）：实际加速比 ≈ 带宽比值 × 0.8~0.95

### 选型建议

先确定场景 → 确认精度 → 确认是算力瓶颈还是带宽瓶颈 → 确认显存容量够用 → 最后比对应指标。
不要拿一张卡的强项去比另一张卡的弱项。
