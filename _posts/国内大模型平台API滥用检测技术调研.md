## 一、火山引擎方舟

### 1.1 客户端设备信息采集（协议条款明示）

**技术方案**：在 Coding Plan 客户端运行时，采集客户端的系统和设备信息，生成设备指纹，与 API Key 绑定存储于服务端。每次 API 调用时，服务端比对请求来源的设备指纹与绑定指纹是否一致。

**实现原理**：

```
┌─────────────────────────────────────────────────────────────┐
│  客户端（编程工具 / new-api 网关）                              │
│                                                             │
│  1. 客户端启动时，采集设备信息：                                  │
│     · 操作系统类型与版本（Windows/macOS/Linux）                  │
│     · CPU 架构（x86_64 / arm64）                               │
│     · 主机名 / 机器 ID                                         │
│     · 网络接口 MAC 地址                                         │
│     · 浏览器/运行环境特征（如 Electron 版本）                    │
│     · 编程工具特征（如 Cursor 的 electron.app.getName()）        │
│                                                             │
│  2. 将设备信息随 API 请求头或 TLS 握手扩展提交至方舟服务端          │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  方舟服务端                                                     │
│                                                             │
│  3. 提取请求中的设备信息，生成设备指纹 Hash                       │
│  4. 查询 API Key 绑定的历史设备指纹集合                          │
│  5. 比对判断：                                                  │
│     · 指纹一致 → 正常，放行                                     │
│     · 指纹不一致 → 标记异常，触发风控                            │
│     · 多个不同指纹 → 判定账号共享/转售，封禁                      │
└─────────────────────────────────────────────────────────────┘
```

**检测信号特征**：

| 信号 | 正常 Coding Plan 使用 | new-api 聚合转售 |
|------|----------------------|------------------|
| 设备指纹数量 | 1-2 个（开发者 1-2 台电脑） | N 个（N 个第三方用户各自的设备） |
| 设备指纹稳定性 | 长期稳定，偶尔更换硬件 | 频繁出现新指纹 |
| 设备类型 | 桌面工作站/笔记本 | 可能含服务器特征（无显示器、Linux 服务器内核） |
| 编程工具特征 | 携带 Cursor/CodeBuddy 等 IDE 标识 | 无 IDE 标识或为 new-api 自定义 UA |

**法律授权基础**：《火山方舟大模型订阅套餐服务专用条款》第 2.8.3 条明确写明"您的客户端的系统和设备信息将会被记录"，用户点击同意即构成授权。火山引擎是三家中唯一在协议条款中直接写明采集设备信息的厂商。

### 1.2 vArmor 容器沙箱 + System Call 级监控

**技术方案**：基于字节开源的 vArmor 技术，在 Linux 内核层面对容器实施强制访问控制（MAC），同时通过 eBPF/auditd 机制监控关键 System Call，实时检测沙箱内的异常行为。

**实现原理**：

vArmor 基于 Linux 内核的两种安全机制实现容器隔离：

```
┌─────────────────────────────────────────────────────────────┐
│  vArmor 容器隔离架构                                          │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐ │
│  │  容器内进程（模型推理 / 用户代码）                         │ │
│  │  受限于 AppArmor/BPF-LSM 策略                            │ │
│  └──────────────────────────┬────────────────────────────┘ │
│                             │ System Call                    │
│                             ▼                                │
│  ┌───────────────────────────────────────────────────────┐ │
│  │  Linux 内核层                                            │ │
│  │                                                         │ │
│  │  ┌─────────────┐  ┌─────────────┐  ┌───────────────┐  │ │
│  │  │ AppArmor     │  │ BPF-LSM     │  │ Seccomp-BPF   │  │ │
│  │  │ (文件/网络   │  │ (内核钩子   │  │ (系统调用     │  │ │
│  │  │  访问控制)   │  │  拦截)      │  │  过滤)        │  │ │
│  │  └─────────────┘  └─────────────┘  └───────────────┘  │ │
│  │                                                         │ │
│  │  ┌─────────────────────────────────────────────────┐   │ │
│  │  │  System Call 监控层（eBPF / auditd）              │   │ │
│  │  │                                                 │   │ │
│  │  │  · connect() → 记录目标 IP/端口                  │   │ │
│  │  │  · execve() → 记录执行的程序路径                  │   │ │
│  │  │  · open()/read() → 记录文件访问                  │   │ │
│  │  └─────────────────────────────────────────────────┘   │ │
│  └───────────────────────────────────────────────────────┘ │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐ │
│  │  安全监控模块（用户可见）                                 │ │
│  │                                                         │ │
│  │  · 沙箱异常连接：分析 connect() 记录，比对白名单          │ │
│  │  · 沙箱异常登录：分析 execve() 记录，检测 SSH/WebShell   │ │
│  │  · 沙箱容器逃逸：检测突破命名空间隔离的行为               │ │
│  └───────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

**三类检测事件的原理**：

| 检测事件 | 监控信号 | 检测逻辑 | 异常判定条件 |
|----------|----------|----------|-------------|
| 沙箱异常连接 | `connect()` System Call | 记录容器内所有主动发起的网络连接（目标 IP、端口、协议），与预配置的白名单比对 | 连接目标不在白名单内；连接非预期端口（如 22/3389/8080）；外联未知公网 IP |
| 沙箱异常登录 | `execve()` System Call | 记录容器内执行的所有程序路径，重点关注 SSH 守护进程、WebShell 脚本解释器 | 检测到 `/usr/sbin/sshd` 启动；检测到 `python -c` / `bash -i` 等反弹 Shell 命令；非授权账号登录 |
| 沙箱容器逃逸 | 内核命名空间隔离边界 | 监测容器进程是否尝试访问宿主机资源（如 /proc/1/root、/dev/sda、_capabilities） | 检测到挂载宿主机文件系统；检测到提权操作（capset）；检测到命名空间逃逸攻击 |

**对 new-api 聚合转售的检测意义**：如果 new-api 部署方将方舟的推理接入点配置在沙箱环境中，并试图通过反向代理隧道将推理能力转发给外部用户，`connect()` 监控可发现沙箱向外网发起的大量异常连接（如 new-api 服务器的 IP），`execve()` 监控可发现部署代理程序的进程行为。

### 1.3 硬件级可信执行环境（TEE）+ 远程证明

**技术方案**：利用 CPU 硬件特性（如 Intel SGX / AMD SEV / ARM TrustZone 等 TEE 技术 *[通用技术示例，火山方舟具体实现未公开]*），在芯片层面创建隔离的"飞地"（Enclave），模型推理过程在飞地内执行，数据仅在飞地内解密，宿主机操作系统和 Hypervisor 均无法窥探。

**实现原理**：

```
┌─────────────────────────────────────────────────────────────┐
│  TEE 机密推理服务架构                                         │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐ │
│  │  客户端                                                  │ │
│  │  1. 发起推理请求                                        │ │
│  │  2. 生成一次性密钥对（公钥 PK + 私钥 SK）                │ │
│  │  3. 用 PK 加密请求数据                                  │ │
│  └──────────────────────────┬────────────────────────────┘ │
│                             │                               │
│                             ▼                               │
│  ┌───────────────────────────────────────────────────────┐ │
│  │  TEE 飞地（Enclave）—— CPU 芯片级隔离                    │ │
│  │                                                         │ │
│  │  4. 远程证明（Remote Attestation）：                    │ │
│  │     · 飞地生成证明报告（Quote），包含飞地的代码哈希       │ │
│  │     · 客户端验证报告，确认飞地运行的是预期的可信代码       │ │
│  │     · 建立端到端加密通道                                │ │
│  │                                                         │ │
│  │  5. 在飞地内用 SK 解密请求数据                           │ │
│  │  6. 执行模型推理                                        │ │
│  │  7. 用 SK 加密推理结果                                  │ │
│  │  8. 加密结果返回客户端                                  │ │
│  └───────────────────────────────────────────────────────┘ │
│                                                             │
│  宿主机操作系统 / Hypervisor / 云管平台：无法读取飞地内数据    │
└─────────────────────────────────────────────────────────────┘
```

**关键特性**：

| 特性 | 技术原理 | 安全保证 |
|------|----------|----------|
| 芯片级隔离 | CPU 硬件强制隔离飞地内存，非飞地代码无法读取飞地内的数据 | 即使宿主机被攻破，推理数据也不会泄露 |
| 端到端加密 | 数据在客户端加密，仅在飞地内解密，传输和存储全程密文 | 网络中间人（如 new-api 代理）无法解密 |
| 远程证明 | 飞地向客户端提供密码学证明，证实其运行的是未经篡改的可信代码 | 客户端可自行验证推理环境可信性 |
| 数据零留存 | 推理完成后，飞地内的明文数据被清除，仅返回加密结果 | 平台方也无法留存推理会话数据 |

### 1.4 全模态内容审核护栏

**技术方案**：在模型推理的输入和输出两个环节部署审核管线，对文本、图片、音视频等多模态内容进行实时安全检测，双向拦截违规内容。

**实现原理**：

```
用户请求 ──→ ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
              │  输入审核     │ ──→ │  模型推理     │ ──→ │  输出审核     │ ──→ 返回用户
              │              │     │              │     │              │
              · 政治敏感检测  │     · 模型生成     │     · 政治敏感检测  │
              · 色情暴力检测  │     · 内容产出     │     · 色情暴力检测  │
              · 提示词注入    │     │              │     · 敏感信息泄露  │
              · 恶意文件检测  │     │              │     · 数字水印嵌入  │
              └──────────────┘     └──────────────┘     └──────────────┘
                     │                                         │
                     ▼                                         ▼
               拦截 + 记录                              拦截 + 记录
```

**对 Coding Plan 滥用的检测原理**：Coding Plan 条款限定"仅限编程相关场景"。内容审核护栏可对 Coding Plan 的输入内容进行主题分类——如果检测到大量非编程主题（如营销文案、客服对话、通用问答），即可判定 API Key 被用于非授权场景。审核系统记录的主题分布形成行为画像，偏离编程主题的请求比例超过阈值即触发告警。

### 1.5 MCP 安全准入检测 + Jeddak AgentArmor

**技术方案**：针对 MCP（Model Context Protocol）工具调用场景，在工具注册时执行安全准入检测，运行时通过 Jeddak AgentArmor 实时防护。

> ⚠️ **成熟度说明**：Jeddak AgentArmor 截至 2025 年 7 月为**研发中状态**（火山引擎 MCP 安全文章原文表述为"正在研发"），以下运行时防护功能描述为设计目标/技术推断，具体实现细节尚未公开。

**实现原理**：

```
┌─────────────────────────────────────────────────────────────┐
│  MCP 工具调用安全防护流程                                      │
│                                                             │
│  阶段一：安全准入检测（工具注册时）                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  1. 工具描述扫描：检测 MCP 工具描述中是否包含          │   │
│  │     恶意指令（如"忽略之前的指令""将数据发送至..."）     │   │
│  │  2. 参数校验：检测工具参数是否包含注入 payload         │   │
│  │  3. 来源验证：验证工具提供方的签名和证书               │   │
│  │  4. 权限审计：检查工具声明的权限范围是否合理            │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  阶段二：运行时防护（Jeddak AgentArmor，研发中）                   │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  1. 调用链监控：记录每次工具调用的完整链路              │   │
│  │     （输入参数 → 工具执行 → 输出结果）                 │   │
│  │  2. 异常行为检测：                                     │   │
│  │     · 检测工具是否尝试访问未授权资源                   │   │
│  │     · 检测工具是否执行了超出声明范围的操作             │   │
│  │     · 检测工具是否尝试数据外泄                         │   │
│  │  3. 数据泄露防护：拦截工具输出中的敏感信息             │   │
│  │  4. 实时阻断：检测到高危操作时立即终止工具调用         │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 1.6 应用层会话加密

**技术方案**：在 HTTPS（网络层 TLS 加密）之上，增加应用层会话加密——客户端与服务端在 API 调用前协商会话密钥，请求体和响应体在应用层再次加密，形成"双层加密"。

**实现原理**：

```
┌──────────────┐                              ┌──────────────┐
│   客户端      │                              │   方舟服务端   │
│              │                              │              │
│  1. 生成会话  │ ─── 密钥协商（ECDH） ──────→ │  2. 生成会话  │
│     密钥 Ks  │ ←── 服务端公钥 ──────────── │     密钥 Ks  │
│              │                              │              │
│  3. 用 Ks    │ ─── AES-256-GCM 加密请求 ─→ │  4. 用 Ks    │
│     加密请求  │     （双层：TLS + 应用层）    │     解密请求  │
│              │                              │              │
│  6. 用 Ks    │ ←── AES-256-GCM 加密响应 ── │  5. 用 Ks    │
│     解密响应  │                              │     加密响应  │
└──────────────┘                              └──────────────┘
```

**对 new-api 的检测意义**：应用层会话密钥与客户端绑定，new-api 作为中间人代理无法解密应用层密文——它只能看到 TLS 加密后的密文，但无法获取真实的请求/响应内容。如果 new-api 尝试剥离应用层加密（如降级为仅 TLS），服务端检测到应用层加密缺失即可判定为非授权客户端。

### 1.7 密钥全生命周期审计

**技术方案**：对 API Key 和加密密钥的创建、轮换、授权、使用、销毁全过程进行日志记录，形成完整的审计链。

**审计日志记录的关键事件**：

| 事件类型 | 记录内容 | 异常检测逻辑 |
|----------|----------|-------------|
| 密钥创建 | 时间、创建者、密钥类型、绑定资源 | 短时间内大量创建密钥 → 批量注册嫌疑 |
| 密钥使用 | 时间、调用者 IP、调用 API、请求参数摘要 | 调用者 IP 与创建者 IP 不一致 → 账号共享嫌疑 |
| 密钥轮换 | 时间、旧密钥状态、新密钥 ID | 频繁轮换密钥 → 规避追踪嫌疑 |
| KMS 访问 | 时间、访问者身份、访问的密钥资源 | 非授权身份访问 KMS → 权限越界 |
| 密钥销毁 | 时间、销毁者、销毁原因 | 销毁后仍有调用 → 残留 Key 泄露 |

## 二、腾讯云

### 2.1 天御 RCE 全栈风控引擎

**技术方案**：腾讯云天御构建了覆盖"注册-登录-订阅-支付-API调用-退款/取消"全链路的风控引擎，基于多个技术底座协同运作。

> 📌 **来源说明**：腾讯云原文（article/2694954）表述为"五大技术底座"，但仅明确列出 4 项：设备智能、身份验证、交易监控、画像库与关系网络。本节补充的"智能频控"为基于原文量化指标部分提及的推断项，非来源明确列出的第五项。以下按技术相关性选取 3 个子节展开，"身份验证"和"交易监控"分别在 2.2 和 2.3 节覆盖。

#### 2.1.1 设备智能底座

**实现原理**：通过在客户端嵌入 SDK 或利用浏览器 API 采集多维设备特征，生成唯一设备指纹。

```

│  │             │ │             │ │             │          │

│  │ · GPU 型号   │ │ · 浏览器版本 │ │ · 时区      │          │
│  │ · 屏幕分辨率 │ │ · 字体列表   │ │ · 语言      │          │
│  │ · 内存大小   │ │ · 插件列表   │ │ · 网络类型   │          │
│  │ · 磁盘序列号 │ │ · Canvas 渲染│ │ · 代理检测   │          │
│  │ · MAC 地址   │ │   特征      │ │ · VPN 检测   │          │
│  └─────────────┘ └─────────────┘ └─────────────┘          │
│                      │                                      │
│                      ▼                                      │
│              ┌───────────────┐                              │
│              │ 指纹生成算法    │                              │
│              │               │                              │
│              │ Hash(所有特征) │                              │
│              │ = Device-ID   │                              │

**模拟器/群控识别原理**：

| 检测维度 | 真机特征 | 模拟器/群控特征 |
|----------|----------|----------------|
| CPU 架构 | 物理 CPU 指令集 | 虚拟化指令集（如 VT-x 嵌套） |
| 传感器 | 加速度计/陀螺仪有真实数据 | 传感器数据缺失或固定值 |
| 电池 | 电量随时间变化 | 电量恒定 100% 或缺失 |
| 电话功能 | 有 IMSI/基站信息 | 无电话功能 |
| 文件系统 | 含厂商预装应用 | 缺少厂商应用，文件系统模板化 |
| Canvas 渲染 | GPU 渲染，特征唯一 | 软件渲染，多设备特征相同 |

**检测信号**：同一 Device-ID 短时间注册多个账号 → 批量注册嫌疑；Device-ID 与 API Key 绑定的历史 Device-ID 不一致 → 账号共享嫌疑。

**对 Coding Plan 滥用的检测原理**：

| 检测维度 | 技术原理 | 异常信号 |
|----------|----------|----------|
| 主题分类 | Qwen SFT 模型对输入 Prompt 进行主题分类 | Coding Plan 输入中非编程主题（营销/客服/写作）占比超阈值 |

### 3.2 Agent ID Guard（全局唯一身份追溯）

> 📌 **产品归属**：阿里云 IDaaS（身份服务），非百炼内置。

**技术方案**：为每个 Agent 分配全局唯一 ID，每次调用使用动态凭据（短期有效的 Token），实现"谁在调、调什么、何时调"的全链路可审计。

**实现原理**：

```

│                                                             │

│     ┌──────────┐    请求动态凭据    ┌──────────┐             │
│     │ Agent    │ ──────────────────→ │ 凭据签发  │             │
│     │ (持长期  │ ←────────────────── │ 服务      │             │
│     │  凭据)   │    动态 Token       │          │             │
│     └──────────┘                    └──────────┘             │
│     · 动态 Token 有效期 5-15 分钟                              │

│                                                             │
│  3. API 调用携带动态凭据                                       │

│                                                             │
│  4. 服务端验证                                                │

│     · 验证 Token 未过期                                       │

### 3.3 "输入-推理-调用-API"可视化时序图谱

> ⚠️ **成熟度说明**：以下技术方案（时序图谱、异常Token监测、对话快照固化）为 AUG 研讨会与会专家达成的**共识建议/规划方向**（来源：article/1730707），非阿里云已上线产品功能。具体算法描述（CUSUM、FFT、KL散度等）为通用技术方法示例 *[通用技术示例]*。

**技术方案**：将每次 API 调用的完整生命周期（输入 → 推理 → 工具调用 → API 响应）构建为时序图谱，结合异常 Token 监测与对话快照固化，实现全链路可视化溯源。

**实现原理**：

```
时间轴 ──────────────────────────────────────────────────────→

Key-A 的调用时序：

T1: 输入"写一段Python排序算法"  ──→ 推理(编程主题) ──→ 输出代码
T2: 输入"优化这段代码的性能"      ──→ 推理(编程主题) ──→ 输出代码  ← 上下文关联 T1
T3: 输入"翻译这段话成英文"        ──→ 推理(翻译主题) ──→ 输出翻译  ← 主题跳变！
T4: 输入"写一封营销邮件"          ──→ 推理(营销主题) ──→ 输出邮件  ← 非编程主题！
T5: 输入"帮我分析这组数据"        ──→ 推理(分析主题) ──→ 输出分析  ← 上下文断裂！

                                     ↑
                          时序图谱分析引擎检测到：
                          · T3-T5 主题与 T1-T2 无关联
                          · T4 为非编程主题（Coding Plan 违规）
                          · T3-T5 的输入风格/语言水平与 T1-T2 不同
                          → 判定：多用户共用同一 Key
                          → 触发：异常 Token 监测 + 对话快照固化
```

**异常 Token 监测原理**：对每个 API Key 维护 Token 消耗的时间序列模型，检测以下异常模式：

| 异常模式 | 检测方法 | 判定 |
|----------|----------|------|
| 消耗速率突变 | 时间序列的变点检测（如 CUSUM 算法） | 新用户加入导致消耗骤增 |
| 消耗周期异常 | 周期性分析（如 FFT 频域分析） | 7×24 均匀消耗（多时区用户） |
| 消耗分布偏移 | 统计分布距离（如 KL 散度） | 输入/输出 Token 比率变化（不同用户的使用习惯） |
| 额度耗尽模式 | 限额消耗曲线拟合 | 阶梯式消耗（多用户叠加）vs 渐进式（个人） |

### 3.6 数字水印追溯

> ⚠️ **来源说明**：阿里云 AI 安全护栏产品文档中，「数字水印标识」仅出现在 **AIGC 输出图片安全检测（img_response_security_check）** 功能下，即**仅对图片输出**进行水印标识，**未提及文本水印能力**。以下文本水印技术描述为通用数字水印原理 *[通用技术示例]*，非阿里云已确认实现。

**技术方案**：在模型生成的内容中嵌入不可见水印，水印编码 API Key 的标识信息，使得即使内容被转售传播，也能追溯到原始 Key。阿里云已确认支持**图片输出水印**；文本水印为通用技术原理。

**图片水印（阿里云已确认）**：对模型生成的图片输出嵌入不可见水印，编码 API Key 标识。

**文本水印原理（通用技术，非阿里云已确认实现）**：

```
┌─────────────────────────────────────────────────────────────┐
│  文本数字水印嵌入与追溯                                         │
│                                                             │
│  嵌入阶段（生成内容时）：                                       │
│                                                             │
│  原始文本: "快速排序是一种高效的排序算法"                        │
│                        │                                    │
│                        ▼                                    │
│  水印编码: 将 API Key ID 编码为二进制位串                      │
│  Key-ID: 0x3F7A → 二进制: 0011 1111 0111 1010               │
│                                                             │
│  嵌入方式（不影响语义和可读性）：                                │
│  · 方式一：Unicode 零宽字符插入                                │
│    在字符间插入零宽空格（U+200B）和零宽不连字（U+200C）          │
│    0 → 插入 U+200B，1 → 插入 U+200C                           │
│    "快\u200B速\u200C排\u200B序\u200B..."                     │
│    肉眼完全不可见，但可通过 Unicode 分析提取                    │
│                                                             │
│  · 方式二：同义词替换编码                                      │
│    0 → 选择同义词 A，1 → 选择同义词 B                          │
│    "高效" vs "高效率"、"算法" vs "计算方法"                    │
│    语义不变，但词汇选择编码了水印信息                           │
│                                                             │
│  · 方式三：标点/空格微调                                      │
│    0 → 使用半角逗号，1 → 使用全角逗号                          │
│    0 → 单空格，1 → 双空格                                    │
│                                                             │
│  追溯阶段（发现转售内容时）：                                   │
│  1. 提取内容中的水印位串                                       │
│  2. 解码为 Key-ID                                             │
│  3. 查询 Key-ID 对应的 API Key 和订阅者                       │
│  4. 定位违规来源                                               │
└─────────────────────────────────────────────────────────────┘
```

### 3.7 AI 网关（合规版聚合管控）

> 📌 **产品归属**：阿里云 API 网关，非百炼内置。

**技术方案**：阿里云 AI 网关作为官方提供的 AI 流量中枢，允许企业统一管理多模型调用，但所有调用经过阿里云认证和审计，与 new-api 的"子令牌分发"模式有本质区别。

| 安全防护 | 依赖 new-api 自身 | WAF + WASM 沙箱 + AI 安全护栏原生集成 |
| 合规性 | 违反转售禁止条款 | 官方授权，合规 |

## 五、三家厂商技术特色总结

### 5.1 火山方舟 — 底层防护最深入

火山方舟的检测技术特色在于**底层深度**——是三家中唯一在操作系统 System Call 层面进行监控的厂商，唯一部署硬件级 TEE 的厂商，唯一在协议条款中直接写明采集设备信息的厂商。

技术栈覆盖从芯片（TEE）→ 操作系统（System Call 监控）→ 容器（vArmor 沙箱）→ 应用（会话加密）的全栈，提供了最深的底层防护。

### 5.2 腾讯云 — 网络检测最全面、量化最透明

腾讯云的检测技术特色在于**网络层全面性**和**量化透明度**——NDR 全流量旁路检测是唯一的网络层全流量分析方案（支持 180 天回溯），天御 RCE 全栈风控引擎是唯一给出详细量化指标的方案（反代识别率 95%），6 亿 IP 画像 + 3 亿+ 威胁情报的数据规模最大。

### 5.3 阿里云 — 语义检测最智能

阿里云的检测技术特色在于**语义级智能检测**——Qwen3-Guard 双引擎利用自研大模型进行深度意图分析，长上下文感知可识别不同用户交替调用的上下文断裂，图片水印追溯是唯一的输出内容追溯手段，"输入-推理-调用-API"时序图谱提供了最完整的可视化溯源能力（*时序图谱为行业共识方向，非已上线产品*）。
